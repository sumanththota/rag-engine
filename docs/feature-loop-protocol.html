Feature Loop Protocol (FLP) · operating manual for #9–#12

One agent writes it. A different agent proves it.

Everything in this protocol comes from one rule: the thing that built the feature is never the thing that accepts it. Everything else — the ledger, the labels, the budgets, the escalation ladder — exists to make that rule cheap enough to run on every ticket.

4 layers 5 states 3 memory tiers onboarding read ≤15k tokens cap 8 iterations · 3 verify rounds · 400k tokens · 2h

The loop, as a state machine

GitHub labels are the live state; the repo files are the memory. Each /loop tick reads state, advances exactly one step, and exits. Click a state to see who acts and what has to be true to leave it.

The one thing to never break: the implementer's "tests pass" is not the accept signal. A criterion counts as passed only when the verifier can point at unedited output it produced itself. If a criterion cannot be made to fail under a wrong implementation, it isn't a check — the verifier flags it untestable instead of passing it.

What each layer is responsible for

Loop engineering is L1 + L3 + L4. Adding L2 — and, later, parallel independent reviewers — is what turns it into graph engineering.

L1

Execution — the Ralph mechanism

Same prompt, fresh context, restart on exit, mechanical stop condition. Context is deliberately thrown away every iteration; the ledger is the memory, not the transcript.

fresh context per iterationidempotent promptcheap model
L2

Scheduling — the dependency graph

A durable dependency store that lives outside any agent's context. Dependency resolution is a trigger fired on merge, never a poll of what some agent remembers.

depends_on / blocks in LOOP.mdre-evaluated at merge
L3

Verification gate

Acceptance criteria and the test runner sit outside the implementer's write scope. The gate consumes evidence, not self-report. This is the single highest-leverage correctness control in the whole design.

read-only verifierstrong modelPASS / NEEDS_WORK
L4

Escalation ladder

Scrutiny scales to reversibility and blast radius. Low-risk reversible changes merge automatically; schema, migrations, irreversible and security changes need a human. Uniform gating produces rubber-stamping, which is the same as no gate.

risk-scaled, not uniformhard budget caps

How a brand-new agent learns from the agents before it

Three tiers, in the repo, git-tracked, read by progressive disclosure. The constitution is the only thing always loaded; everything else is pull, not push.

Tier 1 — the constitution

CONVENTIONS.md + CLAUDE.md. A ~100-line index that points at deeper docs. Project-wide non-negotiables. This is where distilled learnings get promoted so future agents get them for free.

Always read.

Tier 2 — per-feature loop records

.loop/<id>/ holds LOOP.md (manifest), journal.md (append-only), retro.md (written at close).

Current feature always; last 5–10 journal entries only.

Tier 3 — the index

.loop/INDEX.md: one row per past feature — outcome, iterations-to-green, rejection rate, key learning, link. The cheap onboarding scan.

Always read; links out only on demand.

The onboarding read, in order

#ReadWhen
1CONVENTIONS.md + CLAUDE.mdAlways
2.loop/INDEX.md — the compressed historyAlways
3The current feature's LOOP.mdAlways
4The last 5–10 entries of journal.mdAlways — the tail, not the file
5retro.md of related past featuresOn demand, matched by tags in the index. Never all of them.

Hard budget: ≤ ~15k tokens before any work begins. If journal.md passes ~2k lines, compact the older entries into a summary block.

Why files, and not PR comments or an external database

Files travel with the code in git, they diff, they audit, they survive a tool change, and they read cold from a fresh context. PR and issue state is used as the live state machine and the audit trail — not as primary memory.

Keeping the memory from rotting

  • Fresh context per iteration prevents context rot. The ledger is memory; the transcript is not.
  • Progressive disclosure: index and summaries always, full journals only on demand, compact past ~2k lines.
  • Explicit supersession: every retro carries a ## Superseded block. When a learning is promoted into the constitution, the retro line is checked off and the older contradicted guidance is marked superseded — so stale rules can't quietly accumulate.
  • Re-simplify on model upgrades: newer models drift less. After each release, re-ask how much of CLAUDE.md is still earning its place.

The files and the two prompts

Copy these straight into the repo. The two prompts are the whole orchestration: one advances state, one refuses to trust it.

.claude/commands/loop.md — state-first, idempotent orchestrator
You are the ORCHESTRATOR for one DAG step. You do NOT write feature code yourself.
Run once, then exit (a fresh context restarts you next tick).

1. READ STATE (no writes yet):
   - gh: list issues #9-#12 with labels; list open PRs and their draft/ready state.
   - .loop/INDEX.md and each open feature's LOOP.md `state`.
2. IDEMPOTENCY: output "NO-OP" and STOP only if there is no state change AND no newly
   ready work. A human label change counts as a change even with no new journal entry.
3. STALENESS: if a feature has sat in agent:in-progress or agent:gate-pending with no new
   journal entry for >30 min, treat it as a dead agent — label agent:blocked, write
   "stalled, no journal entry since <ts>", STOP. Silence is a failure, not a wait.
4. PICK EXACTLY ONE ready DAG step (all depends_on merged; label `ready-for-agent`).
   If none ready, STOP.
5. ADVANCE ONE STEP based on state:
   - ready-for-agent  -> create branch impl/<id>-* yourself (subagent worktrees get
     temporary worktree-* branches and will not land on impl/ on their own); push it with
     `git push -u origin impl/<id>-*` (the branch must exist on the remote before a PR can
     be opened against it); open draft PR early (the verifier posts its verdict there;
     with no PR the verdict has to travel through a human clipboard and gets paraphrased);
     spawn IMPLEMENTER (cheap model, isolation: worktree) and CONFIRM `git worktree list`
     gained an entry — isolation only fires for a dispatched subagent, so a directly-run
     session silently shares your working directory with every other agent. Instruct:
     touch only owned regions; use test-<id>-* fixtures; do NOT boot the shared dev
     server on :8080 — verify via pytest, spinning up a test instance on an ephemeral
     port where a criterion needs one; stamp a start time in the first journal entry and
     append one entry per iteration; set label agent:gate-pending ONLY with every
     self-test green.
   - agent:gate-pending -> FOUR CHECKS FIRST; fail any and label agent:blocked:
     (a) `git diff --name-only master...impl/<id>-*` — every path must fall inside the
         owned regions named in LOOP.md. An out-of-region edit is an escalation trigger,
         not something the implementer may justify in the journal and carry on from.
         If you approve one, record the approval in the journal — an approved escalation
         and a skipped one look identical afterwards.
     (b) fast-forward verify/<id>-* to impl/<id>-* and confirm the diff is EMPTY. A
         verify branch that lags gates stale code and burns a whole round on a finding
         that was already fixed.
     (c) for every criterion in LOOP.md whose verify_via names HTTP or a UI element,
         grep the new/changed test files for a test client, a route call, or that
         element. Zero matches on any such criterion is a block, named specifically —
         "criterion 3 (verify_via: HTTP) has no route-level test in the diff." This is
         a mechanical check on imports and calls, not a read of test quality. Found live
         on #11: six green tests, all calling ThreadStore directly, zero touching a
         route — four of six criteria were untested at the level they were written.
     (d) for any criterion whose verify_via names a UI behavior with no JS test harness
         available in this repo (check: no playwright/jest/selenium config present), a
         pytest cannot be the acceptance evidence. Require instead, in this order:
           1. A static grep confirming the relevant JS function calls the required route.
              Absence is a definite fail. Presence is necessary but not sufficient.
           2. A pytest asserting the route's response actually contains the data the JS
              needs to read — proves the API contract, not the UI behavior itself.
           3. A manual check with pasted actual output (console log, screenshot, or
              response body) in the journal — not "confirmed working." Self-report of
              a browser check is not evidence; the artifact of the check is. The
              ORCHESTRATOR runs this one (the implementer has no browser): start
              `preview_start` config `flp-test-instance` (port 8099, never :8080),
              drive it with the built-in browser, and post the raw output BOTH in the
              journal and as a PR comment headed "orchestrator browser evidence (check
              (d) level 3)" — the verifier cannot read journal.md but can read the PR.
              Stop the instance afterwards.
         All three, not the first one alone. This repo has no JS test harness at all —
         that gap itself is a standing item, not something to route around silently.
     Then spawn VERIFIER (strong model, on verify/<id>-*, Write and Edit disallowed). Run verifier_command. The VERIFIER posts its own raw
     verdict to the PR with gh — you must not relay it, since you only receive its summary
     and relaying would paraphrase the thing that gates the merge.
     PASS -> label agent:verified, mark PR ready. NEEDS_WORK -> label agent:in-progress.
     A criterion marked BLOCKED-ON-<id> in LOOP.md is excluded from the gate-pending and
     PASS tests only under that LOOP.md's carve-out conditions; the PR must not say
     `Closes #N` while one is open. Reaching agent:verified with one open is still a
     stop-and-report for the human, never a merge.
   - agent:verified -> before merging, confirm verify/<id>-* has an EMPTY diff against
     impl/<id>-*; a verifier that edited anything has invalidated its own verdict.
     Then (human, or auto if within blast-radius policy) merge; on merge, re-evaluate DAG:
     any issue whose depends_on are all merged -> label ready-for-agent.
     Write retro.md; update INDEX.md; promote checked learnings into CONVENTIONS.md.
6. VERIFY EVERY PUSH (standing, permanent — applies after ANY agent, implementer or
   verifier, claims work is committed/pushed): never trust the claim. Check origin
   directly:
     git ls-remote origin <branch> | cut -f1
     git rev-parse <branch>
   These must match. If they don't, push it yourself before proceeding. This has now
   failed 3 distinct ways on #11 alone — wrong branch entirely, right branch never
   pushed, verify branch not fast-forwarded — each one invisible from the agent's own
   report. Treat "pushed" as unverified until confirmed against origin, every single
   time, for every agent.
7. STOP CONDITIONS (hard): count this feature's journal entries as iterations; if
   max_iterations is exceeded, or any escalation_trigger fired, label agent:blocked, write
   the reason to journal.md, and STOP for a human. Nothing measures max_tokens or
   wall_clock — read them off the journal yourself at each tick.

Never advance more than one step. Never let the implementer's "tests pass" be the accept signal.
.claude/agents/implementer.md — model: haiku, isolation: worktree
You are the IMPLEMENTER for one Feature Loop Protocol ticket. You do NOT decide whether
your own work is accepted — a separate verifier does, and it will not read your reasoning
or your journal. Evidence only.

0. Your worktree has tracked files plus .env only — no .venv (never copied; its absolute
   paths break). Before anything else: `python -m venv .venv && .venv/bin/pip install -e ".[dev]"`,
   then `.venv/bin/pytest -q` must be green on that fresh venv. If it is red before you
   have touched anything, stop and flag it — do not start work on a red baseline.

1. Read .loop/<id>/LOOP.md. Touch only the owned regions it names. An edit outside them
   is an escalation trigger — stop and flag it, do not justify it in the journal and
   continue. Found live on #9: a two-line pyproject.toml edit was rationalized past
   instead of escalated. The rule is not a judgment call.

2. For EACH acceptance criterion, check its verify_via field before writing any test.
   If verify_via names HTTP or a UI element, your test MUST exercise that surface —
   a real request through a test client, or a real interaction with that element.
   A test that calls the store or service layer underneath it does NOT satisfy a
   criterion written in terms of a route or a UI action, no matter how green it runs.
   Found live on #11: six passing tests, all calling ThreadStore directly, while four
   of six criteria were written in terms of routes that did not exist. The suite was
   100% green and untested at the level the criteria were actually written.

3. Give every new test its own setup and its own cleanup, scoped to its own fixture
   prefix (test-<id>-*). Do not rely on another test's finally block, teardown, or
   ordering. Found live on #9 AND recurred on #11 despite being written into
   CONVENTIONS.md after #9: run each new test file alone, filtered, and reordered
   before claiming done — not just as part of the full suite.

4. Do NOT boot the shared dev server on :8080. Spin up a test instance on an ephemeral
   port where a criterion needs one to be running.

5. Stamp a start time in your first journal entry for this ticket. Append one entry
   per iteration — not one consolidated entry at the end. The journal is the next
   agent's onboarding read; a single retrospective entry is not a readable tail.

6. Set agent:gate-pending ONLY when every self-test is green AND every verify_via:
   HTTP/UI criterion has a test that actually exercises that surface. If a criterion
   is still unmet, say so in the journal and stay in-progress. The ONLY exception is a
   criterion whose LOOP.md entry is marked BLOCKED-ON-<id> (a dependency not yet merged):
   it does not hold up gate-pending, but only if LOOP.md's carve-out conditions are met
   and the journal states "BLOCKED-ON-<id>, not met". Never mark such a criterion met.
   If a UI criterion needs a browser check, do NOT attempt one and do NOT boot a server
   — the orchestrator produces that evidence; your job is the code, the static-grep
   evidence and the route-level tests.

7. Do not open a PR, do not run the verifier, do not label agent:verified. That
   separation is the whole point — hand off, don't self-certify.
.claude/agents/verifier.md — Write and Edit disallowed; Bash allowed for pytest and gh
You are the VERIFIER. A separate implementer claims feature <id> is complete.
You did NOT see how it was built and must NOT trust its self-assessment.
You have NO Write/Edit access. Do NOT read .loop/<id>/journal.md — it is the
implementer's account of its own work, and reading it reintroduces the self-report
this gate exists to remove. You get the criteria, the diff, and the test runner.

1. Read .loop/<id>/LOOP.md acceptance_criteria (the contract, written before code).
2. For EACH criterion, run the real check (verifier_command + the criterion's own steps).
   A criterion passes only with evidence you can point to (unedited test output / exit code).
3. Run verifier_command at least 3 times back to back with nothing else changed. A test
   that passes 6 times and fails twice is not a passing test — it is a nondeterministic
   one, and shipping it means a suite that reddens at random against correct code.
   Nondeterminism is a NEEDS_WORK finding; say which run failed and why.
4. If any criterion says "no regression" or otherwise reaches beyond verifier_command's
   scope, run the FULL suite. A scoped command cannot evidence an unscoped claim.
5. Any criterion you cannot make FAIL under a wrong implementation is not a real check —
   flag it as untestable rather than passing it.
6. A criterion that LOOP.md marks BLOCKED-ON-<id> is neither a pass nor a failure: report
   it on its own line as "BLOCKED-ON-<id> (unmet)", and give PASS/NEEDS_WORK on the
   remaining criteria only. Never fold it into "all criteria met". Unmarked criteria
   have no such exemption. For UI criteria, browser evidence comes from the orchestrator
   as a PR comment headed "orchestrator browser evidence"; repeat check (d) levels 1
   and 2 yourself and treat that comment as level-3 input, not as proof you skip.
   Begin your reply with exactly PASS or NEEDS_WORK on its own line.
   On NEEDS_WORK, list the failing criterion + the raw output; that becomes the
   implementer's next prompt.
7. Do not paraphrase failures into "mostly passing." The raw verdict gates the merge.
8. Post the verdict to the PR yourself: `gh pr comment <n> --body-file -`. Do not hand it
   back for someone else to relay — your caller receives only a summary of you, and a
   summarised verdict is a paraphrased one.

Never boot the shared dev server on :8080 — verify via pytest only, on a test instance
bound to an ephemeral port if a criterion needs a live server.

A worktree carries tracked files only, so a fresh one has no .env and no .venv — pytest fails there before any agent has done anything wrong. .worktreeinclude copies gitignored files matching its patterns (tracked files are never duplicated), which handles .env. The decisions, and what would change them

Move the weights and watch the ranking move. The scores are fixed judgments from the design; the totals recompute live, so they can differ by a few hundredths from the ones written in the doc. The benchmark figures quoted across this page come from that doc's own sources and haven't been re-checked here.

Criteria weights

Where loop memory lives

Weighted total out of 5.

Everything else that was decided

State machine

GitHub labels + PR state, comments as append-only audit

Native, visible to humans and tooling, zero infrastructure for four tickets. An in-repo state file loses on legibility; a dedicated task store only wins at scale.

Flip when concurrent ready-work passes ~8–10, or dependencies span repos.

Verification

Independent verifier agent now, strong model, read-only

Self-report scores ~1.6 and fails outright; same-agent tests are structurally optimistic. Human sign-off stays mandatory on schema and irreversible changes.

Add CI as the deterministic floor the moment it exists — it lifts correctness at near-zero human cost.

Model routing

Cheap implementer, strong verifier and planner

Uniform-strong scores 3.6, uniform-cheap 3.0, split routing 4.1. Loop shape moves cost far more than model choice does.

Promote the implementer a tier if verifier-rejection exceeds ~40% — rework eats the savings.

Parallel vs sequential

Parallelize only independent atomic work; keep dependent decisions sequential

Shared live Postgres with no test isolation makes unbounded parallelism score badly on correctness and blast radius. Ticket-tagged fixtures plus per-agent owned regions in main.py recover most of the throughput safely.

Widen the fan-out once there is real per-agent DB or schema isolation.

Trigger

Poll label and PR state on each /loop tick

Simple, idempotent, and free of the issues.labeled webhook duplicate-firing problem. Four tickets do not justify event plumbing.

Move to webhooks when human merge latency dominates cycle time, or volume passes dozens.

Escalation gating

Risk-scaled ladder

A blanket human gate scores ~3.4 on safety-plus-fatigue; no gate scores ~2.2; the ladder ~4.4. Too many gates produce rubber-stamping, which is the failure the gate was meant to prevent.

Auto-merge reversible low-risk work. Always gate schema, migrations, irreversible and security changes.

Learning capture

Short structured retro, distilled into the constitution and the index

Free-form notes score mid on legibility and durability; capturing nothing forfeits the entire cross-feature ask. The cost risk is extraction time — keep retros short and promote selectively.

Promote at most a few learnings per feature. Everything else stays in the retro or dies there.

Where memory lives

In-repo files as primary, labels and PRs as live state and audit

Files travel with the code, diff, audit, and read cold. The explorer above is this decision — push the scalability weight past ~0.20 and an external store overtakes it.

Adopt an external DAG store when work spans repos or ready-work outgrows labels.

Budgets, triggers, and the numbers that re-tune them

Caps are tripwires, not targets. Hitting one is information, not failure — but only one of them is actually wired to anything.

Declaring a constraint is not enforcing one. Three separate things in this design are YAML that no code reads: model_routing, budgets, and — because it depends on budgets — most of the L4 ladder. A manifest that says max_tokens: 400000 reads like a guardrail and behaves like a comment. Treat the table below as the honest version: one cap is checkable, one is a habit, and two are prompts to look at something yourself.

The same trap catches model_routing (the tier that routes lives in the subagent's own frontmatter) and the read-only verifier (the boundary that holds is the empty diff, not the tool list). Whenever this protocol states a limit, ask what would notice if it were exceeded.

The readiness gate, before any agent touches a ticket

Deferred until it's bigger

  • CI as the deterministic gate floor — add as soon as feasible; this is the cheapest correctness win on the list.
  • Webhooks or GitHub Actions triggers — only when merge latency or ticket volume demands it.
  • An external DAG store — when concurrent ready-work or cross-repo dependencies outgrow labels.
  • Reusable skills extracted from retros, and parallel independent reviewers beyond two agents.
  • Real per-agent DB and test isolation — high value, more setup. Prioritize it if race incidents recur.

Six rules to keep

  1. Do the rubric rewrite and spec freeze first. Acceptance criteria and context cost nothing but thought and move autonomous success more than anything else.
  2. Never let the implementer be the acceptance signal. Stand up the read-only verifier this week.
  3. Route cheap to implement, strong to verify, with hard caps at every level. Loop shape is where cost runs away, not model choice.
  4. Scale human attention to blast radius, not uniformly. Auto-merge reversible work; gate the irreversible.
  5. Close every feature with a short retro that promotes at most a few learnings into the constitution, plus one index row. This is the compounding mechanism.
  6. Log the loop-health metrics, so next month's weights come from your data instead of someone's priors.

Running it

There is no daemon. The loop is a prompt that advances one step and exits, invoked repeatedly — by you at first, by a shell later.

Three things the design doesn't enforce on its own

Discovered while planning the first run

Model routing in LOOP.md is inert

The model_routing block documents intent; nothing reads it. Routing lives in each subagent definition's own frontmatter, and it takes a tier alias — haiku, sonnet, opus, inherit — not a full model string. Set model: there or you get uniform routing and lose the entire cost argument for a cheap implementer while believing you've kept it.

Check it by looking at which model actually ran on the first implementer turn, not at what the manifest says.

Discovered while planning the first run

A summarised verdict is a paraphrased one

Subagents run in their own context and hand the parent back only a summary. Route the verdict through the orchestrator and it arrives compressed — which is exactly the "mostly passing" failure the verifier prompt forbids. The verifier posts to the PR itself with gh, which means it needs Bash, which is why the empty-diff check is the boundary that actually holds.

Same class of problem: the implementer's branch. --worktree creates branches named worktree-* under .claude/worktrees/, and subagent worktrees are temporary — nothing lands you on impl/<id>-* unless the orchestrator creates it.

Discovered while planning the first run

"Read-only verifier" is a soft boundary

Restricting the subagent's tools helps, but anything with a shell can write files regardless. The enforcement that actually holds is structural: the verifier works on verify/<id>-*, and that branch must show an empty diff against the implementer's.

A verifier that edited anything has invalidated its own verdict. Diff the branch before trusting a PASS.

Discovered while planning the first run

The verifier must not read journal.md

The journal is the implementer's account of what it built and why it believes it works. Handing that to the verifier smuggles self-report back through the side door — the exact thing L3 exists to remove. The verifier gets acceptance criteria, the diff, and the test runner.

If a verdict ever cites reasoning the implementer wrote, the gate has already leaked.

Found on the first live feature

Two agents, one working directory

isolation: worktree sits in the implementer's frontmatter and fires only when a subagent is dispatched. Run the implementer and verifier as ordinary sessions and they quietly take turns checking out branches in the same directory — the verifier can pick up the implementer's uncommitted files, and two parallel agents will clobber each other outright.

After spawning, confirm git worktree list gained an entry. If it didn't, the agents are sharing a desk.

Found on the first live feature

The verify branch silently lags

Nothing advances verify/<id>-* when the implementer commits a fix. A verifier pointed at it gates code from two commits ago, correctly re-reports a defect that was already fixed, and burns a whole round. The design states that the two branches match; it never says who makes that true.

Fast-forward and confirm an empty diff before spawning the verifier — same check that catches a verifier which edited something, run at the other end.

Found on the second live feature

Green tests can guard nothing the criteria actually asked for

#11 shipped six passing tests, all calling ThreadStore directly. Four of six acceptance criteria were written in terms of HTTP routes and UI elements that didn't exist yet. The suite was 100% green and 0% relevant to most of what it was supposed to prove — caught only because the verifier built the real app and drove actual HTTP turns instead of trusting the shipped tests.

verify_via on every criterion, and a mechanical grep before gating: a criterion naming HTTP or UI with no test client or route call in the diff is a block, named specifically — not a judgment call on test quality.

Found on the second live feature

A retro learning written in prose still recurred

#9's retro flagged test-ordering fragility from shared, unscoped cleanup. It was checked off and promoted into CONVENTIONS.md — as a sentence. The identical bug shipped again in #11's suite: tests 3–6 depend on test 2's finally block for cleanup, and fail if run alone, filtered, or reordered. Writing a learning down made it archival, not enforced.

Every promoted learning gets a CHECK line the orchestrator can run — a grep, not a sentence. If a learning can't be phrased as something checkable, it belongs at the template or gate level instead, not as prose to remember.

Scope discipline

Timebox the scaffold to half a day

The real failure mode this week isn't a bad loop — it's spending the week building the protocol instead of shipping #9–#12. If step 2 comes back saying most criteria can't be falsified, that is the week's finding, and rewriting four issue bodies beats any amount of loop tuning.

Protocol work that outgrows half a day before #9 ships is over-engineering.

What actually pays this week

Two controls carry almost all the value: falsifiable acceptance criteria, and the independent verifier. Build only those and skip everything else, and you'd capture most of the benefit by Friday.

The ledger compounds on a longer clock. Retros, the index, promoted learnings — that machinery pays back over roughly five to ten features, not four. It will feel like overhead while you build it, and it won't repay inside this week. Keep it anyway, because retrofitting memory onto a running workflow is far worse than starting with it. But write the shortest version that works: a retro that takes twenty minutes will stop being written by feature three.
