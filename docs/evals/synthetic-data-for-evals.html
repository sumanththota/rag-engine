01What "synthetic" means here — and what it doesn't

Per the autopsy's own honest-limitation callout: all 35 existing traces are already synthetic — a seeding script driving hand-picked questions through the real /chat/stream endpoint. "Synthetic" doesn't mean fake retrieval or a mocked LLM; it means the input distribution is authored instead of observed. 03Two ways to turn dimensions into tuples

cross-product + filter

Generate every combination, then prune

Multiply all dimension values (4 × 3 × 3 × 2 × 3 = 216 combos here), then use an LLM pass to drop nonsensical or duplicate-feeling ones down to the batch size you want.

  • Guarantees coverage — no cell of the space goes untested
  • Some combinations are incoherent ("adversarial + confirmed-absent + follow-up") and get filtered anyway
  • Best when you suspect a specific unexplored corner (e.g. persona × corpus-coverage)
direct LLM generation

Ask the model to pick plausible tuples

Give the model the dimension list and ask it to propose N realistic tuples directly, weighted toward combinations a real user would hit.

  • Reads more like real traffic — good for the "single-shot, neutral, common-topic" majority case
  • Risks under-sampling rare-but-important corners (exactly the ones worth 5/35 and 1/35 findings)
  • Cheaper — one LLM call instead of generate-then-filter

In practice: cross-product for the corners you're actively trying to stress (guardrail bypass, no-context follow-up — both still n=1), direct generation for bulk volume toward the 100-trace floor.

05How the synthetic-data market got here

Worth knowing before picking a vendor: most "synthetic data companies" were built for tabular/PII-safe data (finance, healthcare), not eval traces for LLM apps — that's a recent, mostly open-source-tooling offshoot.

2016
Scale AI founded
Human-labeling-as-a-service; later expands into RLHF data and a "high switching cost" enterprise strategy — not primarily an eval-synthesis tool.
2020
Gretel founded
Tabular/PII-safe synthetic data via generative models — privacy-preserving data for training, not LLM eval traces.
2022–2024
Datagen and Synthesis AI stumble
Datagen raised $70M then shut down; both it and Synthesis AI were built around one-time synthetic-image/data sales and failed to adapt when generative AI made ad-hoc, prompt-driven synthesis cheap and commodity.
2023–2024
Eval-native tools emerge, open source
RAGAS ships a TestsetGenerator using knowledge-graph + Evol-Instruct-style question evolution specifically for RAG. DeepEval and promptfoo add synthesizers. Mostly AI open-sources its tabular SDK under Apache 2.0.
2025
NVIDIA acquires Gretel (~$320M+)
Folded into the NVIDIA AI Enterprise stack — synthetic data becomes infrastructure, not a standalone product category.
2026
Shift to "behavioral datasets"
The framing moves past "generate a CSV of questions" toward persona-driven, multi-turn simulation that scores every span of an agent trace (Future AGI's fi.simulate, OpenAI Agents SDK tracing, CrewAI's training harnesses) — closer to what §01–02 above already sketch for this bot.

06Tools that actually fit a RAG eval corpus

RAGAS TestsetGenerator
document-groundedRAG-specific

Builds a knowledge graph from your ingested documents, then applies "evolution" prompts (simple → multi-context → reasoning) to generate QA pairs with controllable difficulty. Closest off-the-shelf match to the corpus-coverage and query-intent dimensions above — worth trialing against handbook_chunks directly since it's document-native, not prompt-only.

Generates test datasets from source documents including multi-turn conversational scenarios — useful for the turn-structure dimension (follow-up cases), runs as a Python library alongside existing test code rather than a hosted platform.

Everything in §01–04 above is this approach, just made explicit — no new tool to install, and it's what produced the existing 35 traces the seeding script already drives through /chat/stream. The realistic next step is extending the same seeding script with the five dimensions, not adopting a new platform.

07Roadmap, with this session's scope carved out

  1. Fix empty-output-as-silent-success in the capture path

    app/main.py bug from the autopsy's §05 step 3 — explicitly out of scope for this pass. Noted here only so growing the corpus doesn't quietly re-surface it as a "new" finding.

  2. Extend the seeding script with the five dimensions above

    Hand-write ~20 tuples first (per Hamel's method), covering every dimension value at least once, biased toward the under-sampled corners: guardrail-bypass-adjacent injection queries and follow-up turns.

  3. Generate the remaining tuples, render to NL, run through /chat/stream

    Two-step generation (tuples → separate NL-rendering call) to avoid repetitive phrasing; run every query through the real pipeline so traces are genuine retrieval + genuine LLM output, matching how the first 35 were captured.

  4. Re-run open + axial coding on all ~100, watch for saturation

    Hamel's actual bar isn't the count, it's whether new traces stop adding new categories. If theme 7 keeps appearing past trace 80, the pool isn't saturated yet regardless of hitting 100.

  5. Triangulate against real production traffic once available

    Per the autopsy's own callout: a seeded corpus can only surface failure modes its author thought to seed. Treat everything above as closing the gap to Hamel's floor, not as a substitute for real usage data.

The ceiling on synthetic data: no dimension framework escapes the fact that a human authored the dimensions. 100 synthetic traces reduce sampling noise in the taxonomy counts; they do not manufacture failure modes nobody thought to seed. The autopsy's guardrail-bypass and no-context-follow-up themes are exactly the kind of thing worth deliberately over-sampling here — precisely because they're rare enough that real traffic might take a long time to hand you a second example.
