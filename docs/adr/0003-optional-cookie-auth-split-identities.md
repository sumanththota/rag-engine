# Optional cookie auth, additive not gating; identities split from users

Adding login exists only to unlock Thread persistence (saving a user's chat history server-side) — chat itself must keep working exactly as today for anonymous visitors, so auth is optional and additive rather than a gate: every route resolves `User | None` via a dependency that never raises, and "logged in" only changes whether a Thread also gets written to Postgres. Rejected gating chat behind login entirely, since that would add friction with no product reason — nothing about answering a question requires knowing who's asking.

Identity is modeled as two tables, `users` and `auth_identities` (`provider`, `provider_uid`, unique per provider), instead of adding `google_id`/`oauth_provider` columns directly to `users`. The split exists specifically to support linking a password account and a Google account that share the same verified email into one `users` row — a single flat table would force picking one login method permanently, or ad-hoc columns per future provider. Consequence: creating a user is now two writes (`users` + `auth_identities`), not one; accepted since it only happens once per identity.
