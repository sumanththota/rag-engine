# Capture traces by direct Postgres writes, not by reading Loki

The project just added a local Loki/Grafana stack for log aggregation, and every request is already tagged with a correlation id (`trace_id`) and a `stage` field, so reusing Loki as the eval trace store was a real option. We rejected it: today's structured logs deliberately record only lengths/counts (`prompt_chars=%d`, `context_chunks=%d`), never the full prompt, chunk text, or generated answer that a Trace needs, and log lines are append-only so they can't hold a PASS/FAIL Annotation that gets edited later. Instead, Phase 1 adds dedicated capture code inside `RagService`'s caller and `chat_stream`'s `event_stream()` that writes full Trace records straight into Postgres, independent of the logging pipeline. Loki/Grafana remains a separate, complementary view for ops debugging, cross-linkable by `trace_id`.
