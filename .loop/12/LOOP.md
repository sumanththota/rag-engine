## Context (progressive disclosure — links, not inlined bodies)
- No client-side sync-tracking by design: every login re-uploads everything; the upsert is a no-op for anything already stored.
- **ONE shared call site (orchestrator ruling 2026-09-19):** the post-login sync fires from a SINGLE client function (e.g. `afterLogin()` in app/templates/index.html) that every auth path calls — NOT duplicated per auth method. Same shared-function principle as #11's thread_id bounds check. Two entry points must reach it: (a) password `POST /login` success; (b) Google OAuth, which is a full-page redirect (no fetch success handler): #10's callback 302s to `/?login=google`, and boot code detects that param and calls the same `afterLogin()`. Do not add sync code inside a per-method handler.
- **HAZARD — ordering vs hydration:** `hydratThreadsFromServer()` (index.html ~L1377) REPLACES localStorage threads with server threads whenever `/me` returns a user. On an OAuth redirect reload it runs at boot, so if it runs before the sync, anonymous Threads are silently overwritten = data loss. `afterLogin()` must do sync → THEN hydrate, and boot must not call hydrate independently ahead of it on a login-marker load.

- **KEYING DESIGN — HUMAN-APPROVED 2026-09-19 (resolves the 422/data-loss defect; escalation trigger 1 "schema/migration touches an existing table" approved for THIS change only).** Human's words: "If confirmed as UNIQUE(user_id, client_id): approved, nullable client_id on threads." Confirmed by the orchestrator against the code, not assumed:
  - **Why per-user, not a bare UNIQUE(client_id):** client ids come from `crypto.randomUUID()` (v4) but index.html's fallback is `"t-" + Date.now() + "-" + Math.random().toString(16).slice(2)` — not globally unique and partly guessable. A table-wide constraint would let user B collide with, or probe for, user A's id. The constraint is `UNIQUE(user_id, client_id)`.
  - **Schema (the ONLY permitted change to an existing table, in `ensure_schema`, idempotent):** `ALTER TABLE threads ADD COLUMN IF NOT EXISTS client_id text` and `CREATE UNIQUE INDEX IF NOT EXISTS threads_user_client_id_uniq ON threads (user_id, client_id)`. Column NULLABLE, no default, no backfill, no NOT NULL, no change to `id`/PK or any other column. Postgres treats NULLs as distinct, so server-created and pre-existing rows (client_id NULL) never conflict. Additive: the shared dev server on :8080 running older code is unaffected.
  - **Server ids stay `bigserial`. Sync NEVER inserts an explicit `id`.** `ClientThread.id` becomes a string (1-128 chars), stored as `client_id`; integer or oversize ids -> 422.
  - **Upsert:** per thread, one transaction: `INSERT INTO threads (user_id, title, client_id) ... ON CONFLICT (user_id, client_id) DO NOTHING RETURNING id`. Inserted -> insert ALL its messages in order. Conflict -> skip the thread and its messages entirely and look up the existing id. REMOVE the current `role`+`content` message dedup: it collapses genuinely repeated messages and violates criterion 4's "identical messages, in order". Never look a thread up by a server id taken from the payload; every query is scoped by `user_id`.
  - **Response:** `{"synced": <newly created thread count>, "threads": [{"client_id": "...", "id": <server id>}, ...]}` covering EVERY submitted thread (new and already-existing) so callers and tests can map ids. List and detail models expose `client_id` (nullable).
  - **Fixed test ids (the human's second condition):** as of 2026-09-19 they are NOT yet fixed — the shipped sync tests hard-code thread ids 1001, 1002, 2001, 3001 and 5001, and `threads_id_seq` last_value is 1809 (2001 is ~190 away), so they would collide with real serial ids and with concurrent full-suite runs (e.g. another ticket's worktree). Under this design they go away by construction: tests send string client ids prefixed `test-12-` and read server ids from the sync response. MECHANICAL CHECK at the gate (orchestrator runs it): `git diff -U0 master...impl/12-* -- tests/test_threads.py | grep -nE '"id": [0-9]{3,}|/threads/[0-9]{3,}|== [0-9]{4}\b'` must print nothing.
  - **Client (afterLogin(), inside the owned region):** send ONLY Threads whose id is a string (client-generated); numeric ids are server Threads already and are excluded; nothing to send -> skip the sync. DATA-LOSS GUARD: if the sync fails (network error or non-2xx) do NOT call `hydratThreadsFromServer()` — leave local Threads intact and warn. Hydrate only after a successful sync or when nothing needed syncing. The 422 defect (real UUID Thread -> 422 -> hydrate wiped localStorage, 1 Thread -> 0) is in PR #20's "orchestrator browser evidence" comment; the same reproduction must now show the Thread on the server and the guard holding.
  - **Interpretation consequence to flag:** issue criterion 4 says "same id". With server-assigned ids the Thread keeps its identity through `client_id` (echoed and equal to the sent id); the server row id differs. That is the reading criterion 4's verify_via now uses.
