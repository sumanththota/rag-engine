Feature Loop Protocol v3 · every audit finding written back in as a field, a check, or a ledger row — never as a paragraph

The lesson that almost repeated itself inside this document.

v2 was built to stop learnings from surviving only as prose. Auditing v2 against v1 found seven places where it had done exactly that anyway — a failure category renamed into a sentence instead of a field, a nuance flattened into a binary, a mechanical check replaced by a policy statement. v3 doesn't add new ideas. It finds the section each of those seven maps to and puts a field, a check, or a ledger row there instead of the paragraph that was standing in for one.

The one rule everything else serves

Unchanged since v1. What changed is how literally the rest of this page now takes it.

The thing that builds a feature is never the thing that accepts it. That includes this document acting on itself: the v2→v3 revision didn't come from a new failed ticket. It came from rereading the v1→v2 diff the way a verifier reads a diff — looking for where a claim was made without a check behind it. Seven places qualified. None of them needed a new idea; all of them needed the idea moved from a sentence into something a machine or a human can point at and confirm.

The loop, as a state machine

Same backbone as v2 — fresh context, one step per tick, mechanical exit, and the isolation-gated fork between agent:reset and agent:blocked. Two things change here in v3: the "claims" transition now has a check behind it, and agent:blocked is no longer a single dead end — see Restart, respec, or bounded round below.

The isolation test decides which exit fires, answered at contract time, not trigger time — unchanged from v2. What v3 adds is upstream of the fork: the "claims" transition itself is now checked, not assumed. See Isolation preflight — a ticket whose isolation claim was never actually verified can fail this fork in either direction, restarting when it should have blocked, or blocking on a false alarm.

Isolation preflight — checked, not just declared

v2's isolation: block let a ticket assert isolation in YAML. v1 already knew two specific ways that assertion goes false without announcing itself: a copied virtualenv, and two agents quietly sharing a working directory. Both are cheap to check and expensive to discover mid-ticket — so v3 checks them, at the two moments they can actually go wrong.

CheckWhenWhat it catches
Virtualenv rebuilt in the worktree, never copiedWorktree creation, before the first commitA copied .venv bakes absolute paths into pyvenv.cfg and its scripts — it can fail silently or import the wrong package tree rather than erroring cleanly.
.worktreeinclude covers .env, and any custom WorktreeCreate hook replicates that copyWorktree creationA fresh worktree has no gitignored files by default, so .env-dependent tests fail before the agent has done anything wrong — and a hook that replaces the default creation logic silently drops .worktreeinclude processing unless it copies .env itself.
git worktree list gained an entry after spawnImmediately after every implementer or verifier spawnTwo agents run as ordinary sessions sharing one directory — the verifier can pick up the implementer's uncommitted files, or two parallel agents clobber each other's checkouts outright.

This is Rule II — separate the roles — enforced at the filesystem, not the prompt. A verifier and implementer told to run in isolation but never checked for it are role-separated only in the instructions. The check is what makes the separation real; without it, the isolation claim that the restart/escalate fork depends on (see state machine) can be false the whole time nobody looked.

What each layer is responsible for

Still five. L4 now recognizes three resolutions instead of one; L5 now applies its own pruning discipline to itself.

L1

Execution

Same prompt, fresh context, restart on exit, mechanical stop condition. Preceded by the isolation preflight — a ticket doesn't enter L1 until its worktree and env are confirmed, not asserted.

L2

Scheduling

A durable dependency store outside any agent's context. Resolution fires on merge, never on a poll of what an agent remembers.

L3

Verification gate

Consumes evidence, not self-report. Seven checks per criterion now, not five — reading the surface named, the assertion actually written, and the mechanism actually guarded, each as its own check rather than one field standing in for all three.

Escalation ladder

Scrutiny scales to reversibility and blast radius. Isolated + reversible resolves itself (reset). Shared or irreversible reaches a human — who now has three named resolutions instead of one undifferentiated "figure it out."

The contract schema — five fields, then seven

v2 made four failure categories from v1's taxonomy into mandatory fields, plus a fifth (mutation_target) that actually did two different jobs under one name. v3 splits that field in two and adds a sixth for the one taxonomy category v2 dropped outright — the manifest itself being under-specified before any code exists.

.loop/<id>/LOOP.md — acceptance_criteria schema
acceptance_criteria:
  - text: "plain-English statement, falsifiable under a wrong implementation"
    verify_via: "the exact surface a test must call — HTTP route / CLI / UI, never the
                 service or store layer, unless the criterion is itself about that layer"
    attacker_perspective: true|false   # ownership/permission criteria only — if true,
                                        # a non-owner attempt is a mandatory test
    seeds_precondition: true|false     # negative-result criteria only — true means the
                                        # test creates the real thing first, then negates it
    shared_surface: "none | name-of-shared-function"  # if this check plausibly
                                        # applies to more than one route/call site, name
                                        # the one function it must live in
    output_shape: "none | name-of-shared-response-model"  # required whenever a
                                        # criterion says a field must be exposed/present in
                                        # output — hand-built per-route JSON has no single
                                        # place an instruction reliably lands; naming the
                                        # shared model is what makes "expose field X" checkable
    assertion_depth: true|false       # required whenever the criterion cites a specific
                                        # check or guard — the verifier reads what the test
                                        # actually asserts, not its name or docstring
    mutation_target: "none | the specific mechanism this criterion actually guards"
                                        # required whenever the criterion asserts a specific
                                        # ENFORCED mechanism (a transaction, an explicit-id
                                        # derivation) — the verifier removes it and confirms
                                        # the dedicated test goes red before trusting it green

A criterion missing any required field is not a criterion yet — the readiness rubric scores it incomplete, same as an unfalsifiable one.

The manifest-level check output_shape alone can't cover

Before the readiness rubric scores a ticket ready, the planner runs a spec-completeness sweep: every field or behavior named anywhere in the design doc is cross-referenced against the criteria list. A named field with no criterion referencing it fails the rubric outright — it does not get discovered as a missing acceptance criterion three rounds into verification, which is how v1 actually lost the round where code_challenge_method was specified but the required openid scope never was.

What each field closes off, by name

FieldCloses off
verify_viaA test suite that's 100% green and 0% relevant — calling the store layer while criteria are written in terms of routes.
attacker_perspectiveA write-side hole going four rounds undetected because every existing test checked what an owner could do, none what a non-owner could.
seeds_preconditionA negative-result test targeting an id guaranteed to never exist — passes trivially regardless of the implementation.
shared_surfaceA fix landing on 2 of 4 routes sharing the identical need, because the check was written per call site instead of once.
output_shape"Expose field X" landing on some hand-built response dicts and not others — a guidance gap in the spec itself, not an implementer error.
assertion_depthA green assertion sitting behind a silently-skipped guard — passing not because the mechanism works, but because the test never exercises the branch that matters.
mutation_targetThe narrower case assertion_depth can't catch on its own: an assertion that reads real, but stays green even after the specific mechanism it claims to guard is removed entirely.

How a brand-new agent learns from the ones before it

Unchanged in shape — three tiers, on disk, git-tracked, read by progressive disclosure.

Tier 1 — the constitution

CONVENTIONS.md + CLAUDE.md. Project-wide non-negotiables, ~100 lines. Where distilled learnings get promoted.

Always read. Subject to the L5 pruning ritual.

Tier 2 — per-feature loop records

.loop/<id>/: LOOP.md (manifest), journal.md (append-only), retro.md (written at close, CHECK line mandatory).

Current feature always; last 5–10 journal entries only.

Tier 3 — the index

.loop/INDEX.md: one row per past feature — outcome, iterations-to-green, rejection rate, key learning, link.

Always read; links out only on demand.

Hard budget: ≤15k tokens before any work begins. Files, not PR comments or a database — they travel with the code, diff, audit, and read cold from a fresh context.

Restart, respec, or bounded round

v2 wrote down the restart-vs-escalate split but left "escalate" as one undifferentiated outcome. That flattened the exact distinction Karpathy's rule V draws — insert a human only when the contract itself is wrong, not when the build is — which is precisely the judgment call v1's #10 needed and #11's retro found again a level up. v3 gives that judgment call a name and a required record, without trying to automate the judgment itself.

Decision

Cap-and-escalate by default; auto-restart only inside proven isolation

A clean restart is only safe when nothing outside the ticket's own worktree and DB-scoped fixtures can be affected. Defaulting to restart on a shared surface risks silently discarding evidence a human needed to see.

Flip per-ticket: once a ticket has real per-agent DB and file-region isolation, verified per Isolation preflight — not just declared — its drift triggers route to agent:reset.

When agent:blocked fires, a human resolves it one of three ways

ResolutionFires whenWhat happens
RespecThe same criterion fails 3 rounds for the same underlying reason each time — the implementer is genuinely stuck, which is evidence the spec itself is wrong.Ticket returns to the readiness rubric. Contract rewritten, not patched. Counts as a fresh cycle.
Bounded round3 rounds each found a different real defect under one criterion's sub-clauses, and mutation testing has already confirmed the underlying route is correct — the trigger fired correctly, but not because anything is stuck.Human approves exactly one more round, scoped to the single remaining named gap. Not a full reopen.
Reject / descopeThe ticket's scope turns out to mix two verification strategies (e.g. pytest-reachable logic and browser-only behavior) that should never have been one ticket.Split at the boundary the failure revealed. Each half re-enters the readiness rubric separately.

The mechanism doesn't get smarter about telling these apart automatically — that judgment is exactly what a human is for. What's mechanical is that the resolution chosen is written into the ticket's retro.md under a required resolution: field, so a rule that says "respec" quietly two tickets in a row is itself a bottleneck-ledger signal, not a pattern only visible to whoever remembers it.

STOP vs. NEEDS_WORK — not every failure is the same failure

Unchanged core distinction from v2. Updated only to reflect the split of mutation_target into two checks — a hollow assertion and a removable mechanism are different failures, so they're different STOP triggers now, not one.

OutcomeFires onWhat happens next
PASSEvery criterion's named surface exercised, all seven per-criterion checks satisfied, evidence reproduced independently.Merge; DAG re-evaluates.
NEEDS_WORKA criterion fails on its own terms — wrong output, missing case, unmet field.Raw evidence becomes the next prompt. Counts against the round cap.
STOPFabricated evidence; a verifier that edited anything; a verify branch diverged without reconciliation; an assertion_depth check finding a hollow guard; a mutation_target test that stays green with the mechanism removed; any origin claim that doesn't match git ls-remote.Immediate human stop — not a block-and-retry. Does not count against the round budget.

The distinction that matters: NEEDS_WORK says the work is wrong. STOP says the report about the work cannot be trusted. Reproducing cited evidence independently, every round, is what makes the difference detectable.

Taste vs. correctness — two channels, never one gate

Unchanged from v2 — nothing in the audit found a problem here, which is itself worth noting: not every section needed a v3.

Readiness rubric — gates entry to the DAG

Acceptance criteria completeness, context sufficiency, and — new in v3 — the spec-completeness sweep. Every axis reduces to something falsifiable.

Consumer: the orchestrator. Output: ready or rewrite.

Craft rubric — informs the backlog, never a verdict

Design, architecture fit, originality of approach — real but not falsifiable by a test. Scored by the planner against reference examples.

Consumer: backlog grooming and planner judgment only. Never wired to PASS/FAIL.

If a taste score ever changes a verifier's verdict, the two channels have merged and the gate has quietly become self-report again.

Pruning the harness — now applied to itself

v2 gave every promoted rule a review date and re-read all four standing files on a model upgrade or every five features. The audit that produced v3 found the one thing this cadence didn't cover: whether L5 itself is worth its own weight yet.

TriggerPass
A CHECK line is promoted into any standing fileTagged with the round/incident that produced it and a review-after date.
A model upgrade landsRe-read CLAUDE.md, implementer.md, verifier.md, and loop.md — ask which lines the new model now does correctly unprompted.
Every N features (start at 5)Same four-file re-read. Verifier-rejection sustained under ~10% is itself a signal some rules stopped being load-bearing.
A rule is removedLogged in the index the same way a promotion is.

Before adding to L5 itself

Two controls carry almost all the measured value: falsifiable acceptance criteria, and the independent verifier. The ledger and the pruning machinery around them compound over roughly five to ten features, not one — it will feel like overhead while you build it, and it won't repay this week.

Apply the same restraint to L5 that L5 applies to everything else. A pruning ritual that takes an hour stops being run by feature three, the same way a retro that takes an hour stops being written. If a proposed addition to the pruning process itself can't be phrased as a short checklist item, it doesn't belong in L5 yet — it belongs in a retro, where it's allowed to stay prose until it's proven worth promoting.

/loop — orchestrator, v3 additions
SPEC-COMPLETENESS SWEEP: before labeling a ticket ready-for-agent, cross-reference
every field or behavior named in the design doc against acceptance_criteria. A
named field with no matching criterion fails the rubric now, not three rounds in.

AFTER EVERY SPAWN: diff `git worktree list` against its state before the spawn.
No new entry means the agents are sharing a desk — treat as STOP, not a retry.

BEFORE SPAWNING A VERIFIER: fast-forward verify/<id>-* and confirm an empty diff
against impl/<id>-*.

ON DRIFT TRIGGER: read isolation.worktree, isolation.venv_rebuilt, and
isolation.db_scope from LOOP.md.
  all true  -> agent:reset  (wipe worktree + scoped DB, restart from LOOP.md)
  any false/unset -> agent:blocked (always; never guess)

ON AGENT:BLOCKED: read the trigger history. Same criterion, same root cause,
3x -> resolution=respec. Same criterion, 3 distinct defects, route already
mutation-confirmed -> resolution=bounded_round. Scope mismatch across
verification strategies -> resolution=reject_descope. Write the resolution
into retro.md before the next ticket starts.

RETRO GATE: before picking up any new ticket, confirm the immediately-prior
merged ticket's retro.md exists, including its resolution field if it was
ever blocked.

ON ANY CITED EVIDENCE: reproduce it yourself before crediting it, every round.
verifier — seven checks per criterion, v3
For each acceptance criterion, before scoring PASS:
  1. verify_via — confirm the test calls the named surface. Grep the diff,
     don't trust the test's name or docstring.
  2. attacker_perspective — if true, confirm a non-owner-perspective test
     exists and fails without the fix.
  3. seeds_precondition — if true, confirm the test creates the real
     precondition before asserting its absence.
  4. shared_surface — if named, confirm every plausible call site uses it,
     not just the one the criterion's example mentioned.
  5. output_shape — if named, confirm the response actually routes through
     that shared model, not a hand-built dict that happens to match today.
  6. assertion_depth — if true, read what the test actually asserts. A
     guard that can silently no-op (an `if` with no `else`, a swallowed
     exception) on the exact input that should fail it is a STOP, not a
     NEEDS_WORK.
  7. mutation_target — if set, remove that mechanism from a scratch copy
     and confirm the dedicated test goes red. Stays green here -> STOP.

Do not read journal.md. It is the implementer's account of its own work —
the gate exists to remove self-report, not launder it through a second file.

Quickstart

Front-loads the expensive-to-discover parts. Two new steps this version — isolation preflight and restraint on L5 — both learned the hard way, both now cheap because they're written down.

Feature Loop Protocol v3 — the same one rule as v1: the agent that builds a feature is never the agent that accepts it. Everything downstream is now the third pass at making that cheap to run without losing what the first two passes paid to learn. Everything on this page is one self-contained HTML file.
